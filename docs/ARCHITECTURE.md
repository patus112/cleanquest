# Architecture and decisions

## Layers

`src/ui/` is React presentation and forms. `src/domain/` owns date/recurrence, scheduling, commands, points and grant reconciliation. `src/data/` supplies the editable family household and 224 Slovak task templates. `src/persistence/` supplies the `Repository` interface, versioned IndexedDB implementation and Zod backup/relationship checks. UI commits command recipes through the repository and renders only committed results. A future backend can implement the same repository boundary; all owned rows carry a household ID, and the MVP validator enforces one installation's scope.

## Transactions and concurrency

Each domain command runs synchronously inside a Dexie read/write transaction spanning all household tables plus binary photos and local safety metadata. Load and save both remain inside that transaction, so a second tab or rapid repeat action reads the latest committed state. A recipe exception, quota error or relationship violation aborts the transaction. A canonically unchanged command performs no write and does not advance the data revision. Templates live in a separate versioned table and are reseeded without changing household data. `BroadcastChannel` refreshes other open tabs. Local state is not treated as authoritative until persistence succeeds.

Dexie version 1 defines entity indexes. Version 2 adds laundry parent/time indexes and explicit legacy timezone/long-task defaults. Version 3 adds saved weekly rest-day defaults. Version 4 backfills original object IDs/names on available daily and weekly occurrences without changing their identities, durations or rewards. New room fields are optional, preserving unknown details in older homes. Version 5 adds binary `photos` and independent `safety` tables and converts all legacy room/object/problem/Mega photos transactionally. Existing rewards and IDs are preserved. Migration tests cover versions 1, 3 and 4.

## Recurrence and snapshots

Calendar days are `yyyy-MM-dd`, separate from ISO instants used for audit history and appliance cycle deadlines. The household timezone controls the current date; device travel does not silently move it. date-fns operates on date-only calendar intervals, without adding a fixed number of milliseconds across DST. Calendar month/year recurrence always advances from the original anchor to preserve the 31st and February 29.

A deterministic score chooses due, enabled, safe, room-relevant tasks within the budget. Hygiene, capped overdue age, energy and room diversity influence ranking. A simulation advances task due dates to build the week's occurrences. It does not alter actual task recurrence. Snapshots remain stable after creation, with explicit replacement/postponement recorded in the daily plan. Actual completion advances the underlying task. One task per real day prevents repeatedly completing missed daily instances in one session. Older-week snapshots remain historical; the due task is budgeted afresh in a later week.

## Room visualization

`domain/rooms.ts` saves configured room features and creates relevant floor, carpet, curtain and blind inventory entries idempotently. Generation and scheduling respect explicitly absent textiles. Room surfaces and glazing metadata never create inferred glass panels. `ui/RoomVisual.tsx` renders offline SVG pictograms and a schematic floor map from configured records. Explicit normalized object positions override stable automatic ordering; this is not a measured floor plan or a reconstruction from photos. Occurrence object references are saved independently of mutable task associations, so old plans never silently highlight a different target. Missing historical rooms/objects degrade to a named explanation. Color indicators always have accompanying labels and image descriptions.

`ui/RoomLayoutEditor.tsx` keeps an uncommitted layout draft with touch/mouse pointer capture, keyboard nudges and explicit save/cancel. Canvas gestures are constrained only while editing; positions stay inside the room. The repository transaction validates every draft object before saving any changes. `moveObject`/`saveObject` move live task and problem associations atomically with the object, reset its position in the destination, and update only location metadata of unfinished occurrence snapshots. Required IDs, dates, durations, DA and reward obligations stay intact. Completed snapshots and completion history keep their original location. Undoing a completion resynchronizes the reopened occurrence with the object's current room.

## Points and grants

The user sees DA ⚡. Internally `xp` is a compatibility field, not a second currency. Points are derived from non-undone completion records plus eligible weekly and monthly quest flags, never incremented blindly in UI. Achievements derive from eligible completions, excluding extras. Required occurrence completion is idempotent by occurrence ID. Repeated manual/extra actions use task/day IDs and same-day guards; manual rewarded duration is capped by the agreed daily budget.

Integer cents are used everywhere. Each weekly/bonus grant has a stable source ID. Reconciliation compares the desired grant against the source's signed ledger total and appends only the difference. A full week requires a nonempty immutable required snapshot and 100% actual required completion. Bonus steps are independent and bounded by one week. Undo can append a negative correction even after redemption; preserving this debt is more truthful than silently discarding a user's recorded spending. Further redemption cannot exceed available balance.

## Backup and PWA

ZIP format version 1 contains a manifest, data schema version 2 and separate optimized raster bytes. SHA-256 protects the data/photo payloads and the normalized manifest. A bounded central-directory preflight rejects unexpected/duplicate paths and excessive expansion before decompression. The importer stages records in memory, hydrates photo references, then validates required fields, ownership, relations, record counts and duplicate occurrences. A missing task/object/room referenced by historical snapshots is intentional and permitted; a live task pointing to a missing room is rejected. Legacy JSON envelopes 1 and 2 are accepted through the explicit legacy adapter, without claiming checksum verification.

Export obtains household records and safety metadata in one consistent read transaction. No compression or WebCrypto work runs inside a live IndexedDB write transaction. User-confirmed replacement writes all records/assets, reads them back, and compares canonical contents before committing; failed writes or failed verification roll back the entire transaction, including revision metadata. UI only publishes committed results. Photo bytes are kept separately in IndexedDB; the repository hydrates display URLs at the presentation boundary for existing domain compatibility.

`LocalSafety` tracks the current revision, dirty timestamp, prepared export identity/revision/time, explicit saved confirmation, reminder preferences and postponement. Confirming an older export never confirms subsequent edits. Export preparation and postponement do not dirty household records; changing backup preferences does. Archived confirmations retain their original dates/identities on restore, with revision identities mapped to the restored content. Reminder display is restricted to the dashboard outside any focus/dialog session. Browser quota/persistence APIs are optional and separate from domain writes. See BACKUPS.md for exact format and limits.

The build precaches all application chunks and original icons. No remote fonts, authentication or external API is required. The prompt strategy leaves a new worker waiting until the user chooses Aktualizovať. Initial activation claims clients; subsequent activation occurs after confirmation, and Workbox removes obsolete caches. Base-path configuration is shared by assets, scope and start URL. Hash navigation avoids server-side routing requirements. Deployment is guarded by the repository's approval variable.
